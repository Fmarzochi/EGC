# Changelog

All notable changes to EGC are documented here.

## [Unreleased]

### Added

- **One table of every install path, checked by CI** (closes #1714): `manifests/tool-paths.json` lists, for every install target, each path it plans (230 rows over the 29 adapters, the install state of each included), the tool surface it serves and its status: **documented** with the link to the tool's docs that says the tool reads it (checked on 2026-10-10), **egc** for the files of EGC itself under the tool root (hook scripts, install state, library copies the tool does not load), or **unverified** with the reason. `tests/ci/tool-paths-contract.test.js` plans every adapter in every variant the adapters branch on (default, Windows for the Devin user config, `XDG_CONFIG_HOME` and `CRUSH_GLOBAL_CONFIG` for Crush, `KIMI_CODE_HOME` for Kimi, `TRAE_ENV=cn` for Trae) and fails when a planned path is outside the table or a row matches no planned path, so a wrong path fails the build instead of reaching users. `docs/spec/tool-paths.md` is generated from the table (`node scripts/ci/generate-tool-paths-doc.js`, checked by the same test), and `schemas/tool-paths.schema.json` requires a docs link on every documented row and a note on every other one.
- **The hook surfaces of the tools are written by the person and the installer, not by the agent** (#1775): the configuration each tool reads its hooks from (the `settings.json` of Claude Code, with its `.claude/hooks` directory, CodeBuddy and Qwen Code; the `hooks.json` of Codex, Antigravity, Cursor, Copilot, Devin Desktop, Trae and OpenHands; the `config.json` of Devin Local and Junie; the agent files and hook panel of Kiro; the hooks directory of Cline; `crush.json` wherever it is; the plugin directories of OpenCode, Amp and Goose) and the `scripts/hooks`, `scripts/lib`, `egc/hooks` and `egc/lib` directories EGC installs under each tool root are protected from a write by the agent the way `.git/hooks` is: refused through the Write and Edit tools and through the shell (`cp`, `tee`, `sed -i`, a redirection, `ln`), read freely, with the write hook naming the surface as the reason. A surface is judged by its name as well as by where it really is, so a hook script that is a link elsewhere, or a tool directory that is itself a link, is refused too. A repository of its own keeps its `scripts/hooks`, `hooks/hooks.json` and `.opencode/plugins` writable. `tests/egc-guardian-hook-surfaces.test.js` walks 37 configurations, 20 script directories, 18 neighbouring files and the link cases.
- **Kimi Code CLI joins as a home-scoped install target** (#1727, closes #1492, carrying forward the work of @Maqbool61): `egc install` detects Kimi Code CLI (MoonshotAI/kimi-code) and installs everything under `~/.kimi-code`, which `KIMI_CODE_HOME` relocates, read through the adapter's `resolveRoot` so the override reaches every method and the whole install plan, with a leading tilde expanded to the home directory. Skills install flat (the source category stripped); agents, commands and rules land as library folders; MCP servers register in `~/.kimi-code/mcp.json` (or `$KIMI_CODE_HOME/mcp.json`) in the standard `{mcpServers: {}}` shape, and an out-of-home `KIMI_CODE_HOME` is allowed to reach it. The `config.toml` hook surface (a `[[hooks]]` array) is deferred pending machine verification of the TOML merge and the Bash matcher, the same way Warp and Qwen defer theirs. The supported tool count moves to 20 (21 install targets), consistent across the README, the package metadata and the specs, and a machine without Kimi gets the same not-detected hint as the other targets.
- **The OpenCode memory protocol lives where OpenCode reads instructions** (#1724, by Akisolu, closes #1674): the cognitive bootstrap that runs with `egc init` writes the protocol to `<OpenCode config dir>/egc-memory.md`, with `XDG_CONFIG_HOME` respected, and lists that file in the `instructions` of the OpenCode config file (`opencode.json`, or the legacy `config.json` when only that exists) under the same rules as the MCP registration: a config that leads outside the home or `XDG_CONFIG_HOME` is refused before the first write, an `instructions` key that is not a list leaves the file untouched, a second run rewrites nothing, and an `opencode.jsonc` with its own `instructions` list is never edited (the install prints the line to add). The legacy `~/.opencode/instructions/EGC_MEMORY.md` is retired, by its EGC marker only, once the new file is wired. No `AGENTS.md` is created, so OpenCode keeps reading `~/.claude/CLAUDE.md`.
- **Crush (Charmbracelet) joins as a home-scoped install target** (#1744 by @phaiffer, closes #1491): `egc install --target crush` installs the skills flat in the shared `~/.agents/skills` root, the same root Codex, Goose and OpenHands read, so uninstalling one target keeps what the others use; the agents, commands and rules as library folders under `~/.config/crush`; the Guardian and Token Crusher hooks and the two MCP servers in `crush.json`; and the memory protocol in `~/.config/crush/CRUSH.md`. `CRUSH_GLOBAL_CONFIG` and `XDG_CONFIG_HOME` move the configuration directory the way Crush itself resolves it. The install is gated on Crush being present, with the same not-detected warning and `--require-detected` refusal the other targets have, and the `CRUSH.md` bootstrap follows the same gate as the MCP registration. The supported tool count moves to 21 (22 install targets).
- **Auggie (Augment Code) joins as a home- and project-scoped install target** (closes #1494): `egc install --target auggie` installs skills flat under `.augment/skills/<name>/SKILL.md`, commands flat under `.augment/commands/<name>.md`, and rules flattened (Cursor-style namespaced filenames) under `.augment/rules/*.md`, the three families Auggie reads natively ([Auggie CLI docs](https://docs.augmentcode.com/cli/overview), read on 2026-10-09); agents ship as a library folder under `.augment/agents/`, since Auggie has no native sub-agent catalog. No hook or plugin API with an allow/deny decision is documented, so the Guardian and the Token Crusher are out of scope, the same as Kiro and Devin Desktop. MCP servers register in `~/.augment/settings.json` under the standard `mcpServers` key, the same file `auggie mcp add` itself writes to, leaving every other key in that general settings file untouched. The supported tool count moves to 22 (23 install targets).

### Security

- **The MCP SDK moves to the 1.32 line in the root and in both servers** (#1754, #1753, #1762): `@modelcontextprotocol/sdk` 1.32.0 in the root and Guardian lockfiles and 1.32.1 in the memory server, whose manifest floor rises to `^1.32.0`. `mcp/servers/egc-memory` joins the weekly Dependabot schedule with the minor-and-patch group, so that server receives version updates like the other two manifests (closes #1662). The release workflow pins `anchore/sbom-action` v0.24.3 (#1755).
- **The guarded path on Windows is a credentials file, not the whole roaming profile**: the Guardian's denied-path list named `%APPDATA%` as a whole on Windows; it now names the Devin Desktop credentials file specifically, leaving `%APPDATA%` itself free for the tools, including EGC's own install targets, that write ordinary config there. A `.codebuddy/models.json` credential store joins the same list, on every platform.
- **The installer refuses to run as root**: a real install (not `--dry-run`) run as the root user now stops with a clear message before writing anything, since files written as root in a regular user's home cannot be updated or overwritten by that user afterwards. A container image provisioned as root by design opts back in with `EGC_ALLOW_ROOT=1`.
- **The security assessment now states that the state file's HMAC check fails open by design** (#1821, C05): a missing or mismatched integrity sidecar has always logged a warning and still returned the content rather than blocking the read, since a corrupted or tampered integrity file must never lock a person out of their own memory. The threat table only described the happy path before; it now says so directly, and notes that AES-GCM's own authentication tag already runs on every read before the HMAC is even reached.
- **The standalone Guardian CLI now writes its own denials to the audit log**: every harness hook enforcing Guardian rules without an MCP server running (the Bash and write hooks, and every tool-specific adapter that routes through the same CLI) now logs a denied command or write the same way the MCP server's interactive session already does, with the same redaction of secret-looking values.

### Fixed

- **Session bus locks expire by the sweep's clock, and error patterns ignore file paths** (#1848, closes #1681): `sweepDead` took a clock but expired locks by SQLite's own `now`, so a caller or test that passed one saw a lock survive its ttl; the expiry now binds the clock it is given. The key of a recurring error replaces every file path in the message with `<path>` before taking its first six words, so the same error from three files counts as one pattern instead of three.
- **Hook tests no longer race the four-second validator budget on a loaded runner** (#1847): the suite environment gives the Guardian hook the budget of a CLI probe (30 s), so a hook test judges verdicts, not the speed of the machine it runs on; the tests that exercise the timeout itself keep their own 300 ms. A Windows lane of #1846 fell on `echo 'ls' | sh` because the validator fixture took longer than four seconds to start there. The four seconds a person gets are unchanged.
- **`install.ps1` carries no dead function** (#1845, closes #1658): `Register-McpJson`, left behind when the MCP registration moved to `scripts/lib/mcp-register-cli.js` (#1197), is gone, and so is the `Resolve-PhysicalDirectory` chain (`Get-DirectoryLinkTarget`, `Split-PathSegments`, `Split-LinkTarget`) that lost its caller in the same change; the installer test now fails when the script defines a function nothing calls, and its invalid-JSON guard points at the one writer that still exists, `parseJsonObject` in `scripts/lib/mcp-register.js`, instead of a PowerShell catch block that no longer runs.
- **The June 2026 skill links under `antigravity-cli/skills` go, and a stale managed copy is retired by what EGC wrote** (#1793, closes #1789): the legacy-link migration scans that former link directory under the target root and removes a link whose target is inside the retired `skills/egc` namespace whether it still resolves or already dangles, checked again right before the unlink and never touching what it pointed at; the install state records `contentSha256` on every copied file, so a copy whose source changed in the release that moved it is retired by the hash of what EGC wrote instead of staying forever as if the person had edited it.
- **The catalog index cuts a skill's trigger text after a whole word** (#1829): the generator kept a hard 200-character slice of the "When to Activate" section, so an entry could end in the middle of a word or a path; the cut now lands after a whole word with no trailing space, the continuous-learning entry names `~/.claude/skills/learned/` before the parenthetical so the path survives the cut, and both index files are regenerated after the trigger text of #1794 had left them stale.
- **The engineering-auditor reaches Kiro and Trae, and the manifest says why not Warp and Aider** (closes #1679): the `engineering-auditor` module (the agent and the `engineering-audit` and `engineering-fix` commands) now lists `kiro` and `trae`, where its `agents-core` and `commands-core` dependencies already land, so the files go to `~/.kiro/agents` and `~/.kiro/commands`, and to the project `.trae/agents` and `.trae/commands`, the same shape as every other agent and command there. Warp and Aider take neither its dependencies nor any agent or command module, and the module now records why in a new `unsupportedTargets` field, each reason from the tool's current docs with the link and the date it was read: Warp has no file format for an agent or a custom slash command (its agents load skills, invoked as `/<name>`), and Aider has a fixed set of in-chat commands and no subagents. The `engineering-audit` skill keeps reaching both through `skills-extended`. The schema defines the target list once (`definitions.targetId`) and accepts `unsupportedTargets` (a known target to a reason that carries an https link and a `read on YYYY-MM-DD` date) and the manifest validator fails when a target is listed both as a target and as unsupported.
- **Codex reads the EGC memory protocol** (closes #1708): the cognitive bootstrap wrote the protocol to `persistent_instructions` in `~/.codex/config.toml`, a key that is not in Codex's configuration, so the protocol never reached the model and `codex doctor` counted a startup warning; appended at the end of the file, the line also landed inside the last table when the file had one. The protocol now goes to the top-level `developer_instructions` key, "additional developer instructions injected into the session" in the [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference) (read on 2026-10-10), inserted before the first table. Proved with Codex CLI 0.161.0: with `developer_instructions` the protocol shows up in `codex debug prompt-input` and `codex doctor` loads the configuration cleanly; with `persistent_instructions` it does neither. A `developer_instructions` value the person already set is kept word for word with the protocol appended once and upgraded in place on later runs. An old `persistent_instructions` line is removed only when it holds nothing but text EGC wrote (any version of the protocol, wherever the old append left it); one with text of the person, alone or next to an EGC segment, stays untouched and is reported. A trailing comment on the `developer_instructions` line and a quoted key spelling are kept. An existing `config.toml` is rewritten only after the result is parsed back as TOML, and only when every other key and table is unchanged and the text of the person is still there; a file that is not valid TOML, a layout the installer cannot edit safely, a missing TOML parser, and a multiline or non-string `developer_instructions` are reported and the file is left as it is.
- **An install from npm plans what an install from a clone plans** (#1830, closes #1670): the package ships the `.cursor` tree (the hooks, rules, skills and hooks seed of the Cursor target, 72 files a registry install used to skip without a word, since the installer drops a source the package lacks), and the two context files the memory propagation later fills, the root `AGENTS.md` that Antigravity reads from `~/.gemini` and from a workspace `.agents` directory, and the Cursor project rule `.cursor/rules/egc-context.mdc`, are neither shipped nor copied from a checkout: each is generated at install time from the package's canonical text (`scripts/lib/generated-context-files.js`, the `generate-context-file` operation), left alone once it carries its project-memory section, judged by that structure in `egc doctor` so a populated file is healthy and never rewritten by `egc repair`, and removed by `egc uninstall`. The `EGC: Agent Catalog` of `~/.gemini/AGENTS.md` therefore reaches registry installs too. A generated catalog yields to a file another module copies to the same place, so `~/.agents/AGENTS.md` of the Codex target keeps its rules. The prepack guard honours a plain-path negation in the `files` list, so a populated propagation file inside a shipped directory neither publishes nor blocks the pack. `tests/scripts/packed-install-parity.test.js` packs the tarball and compares the plan of every target against the checkout.
- **CodeBuddy reads the EGC memory protocol and applies the Token Crusher rewrite** (closes #1675): the cognitive bootstrap wrote the protocol to `~/.codebuddy/MEMORY.md`, which CodeBuddy does not load as memory (its `MEMORY.md` is the Auto Memory index), and a rewritten command came back as `hookSpecificOutput.updatedInput`, a field CodeBuddy ignores. CodeBuddy loads the user memory from `~/.codebuddy/CODEBUDDY.md` ([CodeBuddy memory](https://www.codebuddy.ai/docs/cli/memory)) and mutates a tool call from `hookSpecificOutput.modifiedInput` ([CodeBuddy hooks](https://www.codebuddy.ai/docs/cli/hooks)), both read on 2026-10-10. The protocol now goes as a marker block into `~/.codebuddy/CODEBUDDY.md`, keeping whatever the person already wrote there, the same way `~/.claude/CLAUDE.md` is handled. Once it is in place, the old `MEMORY.md` is removed only when it holds nothing but the EGC protocol block; one with any other content stays untouched and is reported, and one without the marker is left alone. The PreToolUse rewrite uses `modifiedInput` when `CODEBUDDY_PROJECT_DIR` is set, which CodeBuddy exports to its hooks, and the output for Claude Code and every other tool is byte for byte the same `updatedInput` envelope. The repository's own `.codebuddy/MEMORY.md` becomes `.codebuddy/CODEBUDDY.md`, the project memory path CodeBuddy reads.

## [1.1.9] - 2026-07-11

### Security

- **`egc-memory`: TOCTOU race in encryption key generation eliminated**: `loadOrCreateEncKey` used to leave a window where a concurrent process (e.g. a background agent's own `egc-memory` server starting before `~/.egc/encryption.key` existed) could read a key file that was created but not yet fully written. In the original exclusive-write approach, it could also silently generate and cache its own discarded key for the rest of the process lifetime. ### New Features

- **`update_state`: recovery path for undecryptable state files**: a state file that fails to decrypt (corrupted, or encrypted under an orphaned key from a race) used to permanently block every future `get_state`/`update_state` call for that project, with no sanctioned way to recover: not through the tool itself, and not through the EGC Guardian, which blocks raw shell access to `~/.egc/state/**` by design. `update_state` now accepts an optional `force: true`: when the existing file cannot be decrypted, it is quarantined (renamed to a `.corrupted-backup-<timestamp>` sibling, never deleted) and the call proceeds as a fresh write instead of aborting forever. ## [1.1.0] - 2026-06-13

### New Tools

- **`compress_observations`** - Compresses raw hook observations into structured typed summaries (`tool_failure`, `tool_success`, `file_edit`, etc.) using rule-based analysis. Reduces token usage when injecting observation history into new sessions. Contributed by [@Kunall7890](https://github.com/Kunall7890).

- **`detect_patterns`** - Analyzes runtime events from the state-store database to surface repeated commands and recurring errors across sessions. Helps identify automation candidates and structural issues that persist between conversations.

- **`working_memory`** - Stores transient context within a session with configurable TTL. Entries expire automatically so the memory store does not accumulate stale data across sessions. Exposed as `working_memory_set`, `working_memory_get`, and `working_memory_list`.

- **`lessons`** - Records cross-session knowledge with confidence decay. Each lesson tracks how many times it was reinforced and when it was last seen; confidence degrades over time so stale lessons surface for review rather than being applied forever. Exposed as `lesson_save`, `lesson_recall`, and `lesson_reinforce`.

- **`search_history`** - Full-text search over stored observations using FTS5 with BM25 ranking. Returns results ordered by relevance rather than recency.

### Memory Improvements

- **Branch-aware project state** - `get_state` and `update_state` scope memory per git branch. Switching branches restores the context for that branch automatically.

- **State consolidation pipeline** - A rule-based layering pipeline compresses and consolidates observations on each `update_state` call, keeping the memory store compact without losing important signals.

- **Deterministic SessionStart hook** - The SessionStart hook that writes context into the active harness settings file now runs idempotently. Re-running install or switching adapters does not duplicate entries.
